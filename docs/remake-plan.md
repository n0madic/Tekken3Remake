# Tekken 3 remake: implementation plan

This document fixes the remake's goals, architecture, code conventions, graphics direction and milestones. The game's behaviour is specified by the research documentation in [`research/`](research/README.md). This plan refers to it and does not restate it.

Date of the decisions: 2026-09-27.

## Goals and non-goals

**Goals**

- **Faithful game logic.** Frame data, move transitions, hit detection, damage, reactions, round flow, CPU decisions, camera rules, mode rules and unlocks behave exactly as in the original (Japan Rev.1 baseline).
- **Modern, resolution-independent presentation.** 3D rendering with current techniques, any aspect ratio, high frame rates, vector HUD and menus.
- **Platforms.** Windows, macOS, Linux, Android, iOS, and the web.
- **Controllers.** Standard gamepads, including DualShock 4 and DualSense over Bluetooth, with vibration. Keyboard on desktop and touch controls on mobile.
- **Open-source code.** The repository contains no original game data. Assets are converted from the owner's disc image (see [Content pipeline](#content-pipeline)).

**Non-goals**

- Emulating the PlayStation hardware (GPU, SPU, GTE, CD timing) or reproducing its rasterisation.
- Copying the structure of the original code. The ports in `tools/research` are **reference implementations** that pin down behaviour. They are not code to translate line by line.

## Key decisions

| Area | Decision | Reason |
|---|---|---|
| Engine | Godot 4, pinned to one minor version (4.7.x at the start). Minor upgrades are a deliberate task. | Open source (MIT); a complete engine with UI, animation, audio, input and editor; all target platforms from one project. |
| Language | GDScript only, statically typed everywhere. Warnings for untyped declarations and unsafe calls are treated as errors. | Required by the web export: C# projects cannot export to the web in Godot 4. Static typing also makes GDScript faster and catches errors early. |
| Logic vs code | The logic is written anew from the documented rules, as idiomatic GDScript. Equality with the original is proven by tests against golden traces, not by code resemblance. | Readable, maintainable code with exact behaviour. |
| Simulation | Fixed 60 Hz step. Integer and fixed-point arithmetic in all logic that affects the game state. No engine time, physics or random functions inside the simulation. | Frame-exact behaviour, replays, and the option of rollback netplay later. |
| Presentation | Rendered at the display rate. Reads the simulation state and may interpolate between two steps. It never writes back. | High refresh rates without changing the game. Graphics can be replaced freely. |
| Renderers | Forward+ on desktop, Mobile on phones and tablets, Compatibility (WebGL 2) on the web. One project with quality presets. | Godot's web export supports only the Compatibility renderer. |
| Assets | Converted once from the user's disc image by a Python script, only what the remake uses. Godot reads the output folder directly and packs it into the PCK when building; the largest binaries (meshes, baked poses) are stored gzip-compressed (`*.bin.gz`). Music and movies are optional, and so is the USA disc for the English game texts. Never committed. Music is Ogg Vorbis, movies are Ogg Theora with Vorbis sound, both played by Godot's own decoders. Without an FFmpeg that encodes Theora and Vorbis the converter falls back to WAV music (QOA at import) and JPEG-frame movies. | No importer to maintain on every platform; a light build without the largest data. Theora and Vorbis play everywhere Godot runs, the web included; the fallback needs no codec at all. |
| Original bugs | Bugs without effect on balance or gameplay (cosmetic, latent, undefined behaviour, dead code) are not reproduced: the remake does what was intended. Bugs that affect gameplay stay by default and are fixed by one option, **Gameplay fixes** ([Original bugs](#original-bugs)). | The original gameplay is preserved; nothing else carries the original's defects. |
| Tests | A small built-in runner (`tests/run_tests.gd`, `TestSuite` base class) run headless by `tools/remake/run_tests.sh`. Golden traces are generated by the verified Python ports. | Godot has no test framework for projects, and the suites need only expectations and trace comparisons, so no external dependency is needed. The Python ports are proven against the game's own code in the CPU harness. |

## Architecture

### Layers

```text
┌──────────────────────────────────────────────────────────────┐
│ app          game-state machine, scene switching, settings   │
├──────────────────────────────────────────────────────────────┤
│ screens      title, menus, select, VS, results, ranking,     │
│              Theater: Control scenes                         │
├──────────────────────────────────────────────────────────────┤
│ presentation fighter / stage / effects / camera views, HUD,  │
│              audio players; reads the sim, consumes events   │
├──────────────────────────────────────────────────────────────┤
│ core (sim)   deterministic simulation: fighters, moves,      │
│              combat, round flow, camera director, AI, rules  │
├──────────────────────────────────────────────────────────────┤
│ content      typed resources: models, motion banks, stages,  │
│              sound banks, tables; loaded from imported data  │
├──────────────────────────────────────────────────────────────┤
│ platform     input devices, vibration, save data, asset      │
│              locations, platform quirks                      │
└──────────────────────────────────────────────────────────────┘
```

Dependencies point downwards only:

- `core` depends on `content` data classes and nothing else. It has no `Node`, scene tree or singleton access.
- `presentation` and `screens` read `core`; `core` never calls them.

### Simulation core

**State as plain data**

- The game state is a tree of typed `RefCounted` objects: `MatchState`, `FighterState` ×2 (×3 in Tekken Ball and Tekken Force), `CameraState`, `AiState`, `EffectSpawnLog`, and the RNG states.
- Each object has `copy_from()` and a compact `serialize()` for snapshots, replays and rollback.
- Field names follow [fighter.md](research/code/fighter.md), in English words rather than offsets.

**One step**

- `Simulation.step(inputs: PackedInt32Array) -> void` advances one frame in the order of `FightFrame` ([fight-frame.md](research/code/fight-frame.md)).
- Everything outside the simulation is passed in: pad states, mode, rule flags.
- Results that leave the simulation (sound requests, effect spawns, vibration patterns, camera shake, round messages) are appended to a per-frame `SimEvents` list. The simulation never plays anything itself.

**The pose pipeline belongs to the simulation.**

- Hit detection reads joint positions. Motion sampling, FK and IK ([animation.md](research/formats/animation.md)) therefore run in `core` with the exact integer rules.
- The presentation copies the resulting 18 joint transforms onto a `Skeleton3D`.

**Numbers**

- Positions, angles (4096 per turn), and 4.12 matrices and vectors stay integers.
- `core/math` holds the few primitives the documented rules need: sine lookup, fixed multiply with the GTE's rounding and saturation, integer square root, and the 4.12 matrix product.
- These primitives are the only places where the documentation's "GTE" semantics live. Everything else uses them by name.

**Randomness**

- Each documented generator is its own object:
  - `rand()` mixed with the AI's LCG `5x + 3` ([ai.md](research/code/ai.md));
  - the camera generator `(x + 1)·0x10DCD` ([camera.md](research/code/camera.md)).
- Their seeds are part of the state.

**Rules**

- `RuleSet` carries the gameplay-fix flags ([Original bugs](#original-bugs)) and region differences (Japan / USA, [usa-version.md](research/code/usa-version.md)).
- The **Gameplay fixes** option sets all gameplay-fix flags at once. The individual flags exist for tests and debugging only.
- Code reads named booleans (`rules.fix_juggle_arc_overflow`), never entry numbers; each flag's doc comment names its entry in `game-bugs.md`.

### Presentation

**Views**

- `FighterView`: the seam-exact skinned mesh with 22 joints (one per draw part), the hands (and the jaw of Kuma, Panda and Gon) as one mesh per vertex variant, an atlas with closed eyes for blinking, and Gon's atlas with his swapped head palette and the patches of his eyes' look direction (`GazeAtlas`).
- `StageView`, `EffectsView`, `CameraRig`, `Hud` and `AudioDirector` each read `core` state after every step.
- They also consume that step's `SimEvents`.

**Interpolation**

- With a display faster than 60 Hz, views interpolate between the previous and the current step (positions, joint rotations, camera).
- A setting turns interpolation off for a strict 60 Hz picture.

**Freedom of presentation**

- Views may add detail without affecting the game: cloth, secondary motion, particles, lights.
- Replacing an original effect with a modern one is a presentation change. Its timing still comes from the simulation.

### Input

- **Pad state.** `InputRouter` turns Godot input actions into one 16-bit pad state per player per frame, the same layout as the original. It keeps two stages: the physical buttons, then the key configuration. Some rules read the physical buttons, such as the Tekken Force manual target switch ([modes.md](research/code/modes.md)).
- **Skipping.** The game skips its start-up, attract sequence, fight replays and movies on Start only; the remake also takes ✕ and ○ there (as Start held with them, before the step), so a modern pad's confirm button works. Replays and traces are unaffected.
- **Device assignment.** Controllers are assigned to players on the first button press. Hot-plugging is supported. The keyboard has two layouts (player 1 and player 2), rebound on the settings' Controls tab (`key_bindings` in `user://settings.json`, applied to `InputRouter.layouts`); gamepads keep the standard SDL mapping.
- **Button glyphs.** The touch buttons show the PlayStation symbols (□ △ ○ ✕) as vector shapes. The remake draws no controls hints over the game (a line of per-device hints was tried and removed in M5, at the owner's request); the game's own screens name the buttons as the original does.
- **Vibration.** The original DualShock scripts (small motor on/off pulses, large motor strength; [sound.md](research/code/sound.md#vibration)) are evaluated in `platform/Rumble` and sent with `Input.start_joy_vibration(weak, strong, duration)` every frame. The touch controls' player feels the phone's own motor (`Input.vibrate_handheld`, Android permission VIBRATE) at the stronger of the two levels, as short pulses renewed while the level holds.
- **Touch.** A virtual stick and four face buttons, L1 L2 over the stick and R2 R1 over the face buttons in one row (in the thumbs' reach on tall screens too; shown only once player 1's key configuration gives them an action, the game's default being NO USE, and always on the KEY CONFIGURATION page), Select and Start at the bottom in the middle, plus macro buttons in the top corners (none, the throws 1+3 and 2+4, or also 1+2 and 3+4; a setting), shown on touch devices (or always, or never: a setting), in one of five sizes (70–130 %, a setting). They are player 1's device in InputRouter: their first press takes player 1, moving a pad or keyboard already there to player 2 when that is free. They hide while the settings screen is open, and over what Start skips (movies, the title, the demonstration, replays) and the records pages without a name to enter only Select and Start stay. Android's Back is Escape except on the main menu (there Escape opens the settings); the game is landscape only (either way up).
- **Web.** The browser's Gamepad API is used through Godot.

### Audio

- **Buses.** Music, SFX, voices and system sounds, with separate volume settings.
- **Sound banks.**
  - The combat bank, the system bank, and one voice bank per character are loaded as `SoundBank` resources: samples with loop points, plus tone parameters.
  - A sound code resolves to a sample, a pitch, a volume and a pan ([sound.md](research/code/sound.md)).
  - The pitch comes from the documented playback-rate rule, which is bit-exact.
- **Voices.** The original plays up to 24 voices. The remake uses Godot polyphony with a per-bus voice limit and the original priority order where it matters, such as announcer calls.
- **Music.** The 32 music tracks map to streamed files with loop flags (a WAV `smpl` loop). The two soundtracks (ARRANGE / ARCADE) are an option, as in the original.
- **Speaker out.** The options' MONO folds the whole mix to mono on the master bus (a stereo-enhance effect with no pan pull-out); STEREO leaves it.

### Content pipeline

The code repository never contains original data. Assets come from a disc image the user owns and are converted **once**, by a Python script, into formats Godot reads natively. There is no importer inside the game.

**Discs**

- **Any one release is enough:** Japan Rev.1, the original Japanese pressing (SLPS-01300) or USA ([disc-variants.md](research/disc-variants.md)). The converter reads the images given with `--image` (one per release, told apart by their contents) and converts the game from the first in that order, from a `.cue` sheet (tracks compressed as ECM, APE, FLAC or WAV are found under the sheet's names; tracks may share a file), a lone data track (raw, ECM, or a 2048-byte ISO without the XA music and movies) or a CHD (through MAME's `chdman`) (`disc_image.py`).
- **One address space.** Japan Rev.1 is the canonical layout: the converter, the remake (`GameRam`) and the docs name data by its addresses. The other releases' executable and overlays are rebased onto it before conversion by a layout (`tools/remake_import/layouts/<release>.json`, made by `layout.py` from both discs; numbers only: runs of equal bytes with their shifts, pointer relocations, text pairs, the hashes of the release's blocks it fits). Pointers are rewritten to Rev.1 addresses; a text longer than Rev.1's place for it is kept aside by address (`screens/ram.json`, read first by `GameRam`); objects whose size differs (picture archives, the system textures) are read from the release's own images; what Rev.1 has and the release lacks is filled from the project (practice's KEY DISPLAY: its label, and the page rows, whose numbers are in usa-version.md), and structural differences go into `layout.EXTRAS` (the original's XA stream table with 16-byte rows).
- **Checked:** conversions from each disc match the Rev.1 conversion but for the release's own content (texts, pictures with text, credits, the original's typos and missing stage band colours); every byte the screens read during the flow traces (`GameRam`) matches, but for texts; the whole test suite, trace comparisons included, passes on a conversion from the USA disc alone.
- **Converted from the USA disc** the game texts are English only (`manifest.json` records the source; the *Game texts* setting has no Japanese); the English move lists stand in for the Japanese ones.

**Conversion**

- `tools/remake_import/convert.py` reuses the verified decoders in `tools/research` (`kmd.py`, `kmd_skin.py`, `motion.py`, `pose.py`, TIM and VAB decoders, `inspect_xas.py`, `move_text.py`).
- **Only what the remake uses is converted.** A manifest in the script lists the used resources: models, costumes, motion banks, stages, sound banks, tables and texts. Data the remake does not use is skipped. This includes development movie layouts, unused music streams 29–31, the empty model rows, and the Theater's Tekken 1 / Tekken 2 disc mode, which would need those discs.
- **Music and movies are optional:**
  - `--no-music` skips the XA music and the CD-DA track;
  - `--no-movies` skips the STR movies.
  - They are the two largest groups and the only ones that need FFmpeg. The converter uses the first FFmpeg on the `PATH` with the Theora and Vorbis encoders (or the one given with `--ffmpeg`), else the first one with the WAV and JPEG-frame fallback.
- **Output.** The converter writes straight into `remake/imported/`, the single location of the remake's assets. There are no other copies, no symlink, and nothing under `work/`. The folder is listed in `.gitignore`. The editor, tests and runs read it directly as `res://imported/`.
- **Godot's own cache.** Godot keeps its engine-format versions of imported files (textures, audio) in `remake/.godot/imported/`. This is Godot's build cache, not a second source, and it is git-ignored as well.
- **Idempotence.** Re-running the script rewrites only changed files and deletes the files it no longer produces, so builds never pack stale data. It refuses to write into a non-empty folder that is not its own: one with neither a `manifest.json` nor the `.converter` marker the script writes before anything else (so that a run that ended early, with no FFmpeg or on Ctrl-C, leaves a folder the next run accepts). A `manifest.json` in the output records the source release and image hash, the script version, and which optional groups are present.

| Source | Converted to |
|---|---|
| `.kmd` models (only the costumes the remake uses) | The remake's own mesh (`model.json` + `mesh.bin`) and a texture atlas. Every corner is one part-local vertex or the 0.5/0.5 blend of two parts' vertices (the seam exchange of `DrawSkinnedPart`). The two halves do not coincide in any single pose (30–150 units apart in real poses), so a glTF skin with one bind position per vertex cannot reproduce the seams. Each corner therefore keeps both part-local positions, and the fighter shader blends them with the two joint matrices. The hand variants only move the hand rows' own vertices (their exchange lists are the base block's in every model), so the faces that use a hand vertex are stored once per variant the hand channels can select (0–9) and swapped as meshes (the arcade's models use its 41 variants and pack them as pose tables: below). Attachments carry their rest angles and dynamics record. |
| TIM textures and CLUTs | Resolved through an emulated VRAM into one atlas per model or panorama: only the rectangle each material (page + CLUT) uses, with a 2-texel edge gutter for filtered sampling. CLUT colour `0x0000` becomes transparent. A costume with closed-eye art gets a second atlas with the closed-eye rectangle copied over the eyes, as the blink's `MoveImage` does. Effect flipbooks become frame strips. |
| Motion banks (`divmot*.bin`) | JSON for the move rows and the slot index (branch rows, events, camera lists and attack descriptors follow in M2). Animation streams are baked once with the verified sampler (`motion.py`, bit-exact with `AnimDecodePose`): every frame's 49-channel pose vector goes into `<bank>.poses.bin`, as [animation.md](research/formats/animation.md) recommends. The remake does not evaluate the B-spline curves. |
| Stage archives and TMDs | The panorama as one mesh (`panorama.bin`) with an atlas of its used texture regions, floor tile pictures, and JSON for the floor pattern, lighting records and the stage's view-coverage data ([Aspect ratios](#aspect-ratios)). |
| EXE and overlay tables | JSON: character records, sound tables, camera presets and lists, AI parameters, effect tables, the sine table, texts. |
| VAB banks | WAV samples at the game's playback rate with loop points, plus a JSON table of the sound codes with their gain. |
| XA music (optional) | Ogg Vorbis at q4 (about 125 kbit/s; the 4-bit XA-ADPCM source is about 300 kbit/s; q6 took 147 MB, q4 takes 92 MB for the 47 streams; chosen by size and SNR (17.5 dB against 21 dB at q6), not by ear: TODO listen to ABX) (decoded by FFmpeg, `adpcm_xa`); looping tracks loop over the whole stream, set by the player from `music.json`. Fallback: WAV with a `smpl` loop, compressed with QOA at import. |
| The USA disc (optional, given with a Japanese one) | `usa/`: the English strings paired with the Japanese ones where both discs, rebased, keep them at one Rev.1 address or in one pointer table entry (`tools/remake_import/usa.py`), the Theater's help lines and the staff roll, the English move lists with their shared atlas and tables, and the pictures with text (`select.tims`, the title pictures, the rules page). |
| Title picture | `icon.png`: the application icon, the TEKKEN 3 logo cut from the title picture, and Android's adaptive layers (`icon_foreground.png` inside the launcher's safe zone, a black `icon_background.png`, `icon_monochrome.png`). Every build uses it: the web page's favicon and touch icon, the macOS `.icns`, the Windows executable's icon, the iOS app icons, the Android launcher icons, and the window icon at run time (builds only; the repository has no icon). |
| Replaceable textures | `texture_index.json`: the converted pictures (fighters, stages, HUD, effect flipbooks, screens) by their key (the SHA-256 of the file), for texture packs. With `--texture-sources <file>` the converter also records where each picture's texels come from in VRAM (`sources.py`: the pieces, their VRAM snapshots and CLUTs, rotations and gutters; the screens' run-time VRAM states), for `texture_pack.py import-duckstation`. |
| STR movies (optional) | Ogg Theora + Vorbis (q4, as the music) at 30 fps, decoded with FFmpeg (`psxstr` demuxer, `mdec`, `adpcm_xa`); each frame is shown from the first 30 fps frame at or after the CD sector at which it arrives (checked against the STR frames). Two qualities: `<name>.large.ogv` (q8) for desktop builds and `<name>.small.ogv` (q6, about 40 % smaller, fine detail softened) for web and mobile builds. Fallback: JPEG frames with their arrival sectors (`<name>.bin`) and the audio as WAV; the player shows the frame due at the audio position. |

**Builds**

- The export packs the converted assets into the game's PCK together with the code. The export presets include the files Godot does not import (`*.json`, `*.bin`, `*.ogv`) explicitly.
- There are three presets per platform:
  - **full**, with music and movies (desktop keeps the large movies, web and mobile the small ones);
  - **nomovies**, which excludes only `imported/movies/` (the music stays);
  - **lite**, which excludes `imported/music/` and `imported/movies/` by export filters.
- **At run time** `AssetCatalog` reads `manifest.json` and reports which groups are present. Without movies, the movie screens are skipped (the attract loop continues with the next step) and the Theater's movie page is hidden. Without music, music calls are silent and the sound player is hidden.
- **Builds are private.** Every build contains converted game data, so builds are for the owner of the disc and are not published. Only the code is public.

### Save data and settings

- Records, unlocks, the ranking and options are stored in `user://` in the remake's own format. The content matches the PSX save block ([modes.md](research/code/modes.md)).
- Two memory cards (the setting *Memory card*, slot 1 `progress.json` or slot 2 `progress2.json`, `app/progress_card.gd`): switching on the settings screen loads that card's progress (a card with no save starts from the defaults) and reopens the main menu through the transition screen. The remake's saving rules, outside `core` so that the traces still hold: AUTO SAVE starts on for a card with no save (the game's default is off), and leaving OPTIONS saves while auto save is on or still on in the file (the game saves only after statistics and unlock updates, so changed options waited for the next fight).
- Settings (`user://settings.json`, the remake's settings screen, opened with Select on the main menu): Gameplay fixes, game texts, interface language, graphics preset, textures, texture pack, fullscreen (desktop; F11 or Alt+Enter on Windows), frame interpolation, framing, four volumes, vibration, touch controls and macros, the keyboard layouts' keys (on two tabs: General, Controls). They are kept separately from game progress.

### Texts and localisation

- **Interface strings** are written for the remake and translated through Godot's translation system (English and Japanese at first; `app/translations.csv`).
- **Game texts** (the setting *Game texts*): the remake keeps one interface, the more complete structure of the two releases (Japan Rev.1's: the team battle round voice, practice's KEY DISPLAY), and with *English* shows the USA release's English wherever it has one ([usa-version.md](research/code/usa-version.md)): menu wording, practice, the records, Tekken Force, the Theater's lines, the staff roll, the English move lists in their own encoding, and the pictures with text (Tekken Ball's rules page, the select screen's names, the title logo). The generic wording is the project's own (`content/texts_en.json`, no Namco property); names, titles, credits, the move lists and the pictures come only from the user's USA disc (given to `convert.py` with the Japanese one); without it those parts stay the Japanese release's. Converted from the USA disc alone, its own texts are the game's and there is no Japanese choice.
- **Game texts** otherwise come from the converter: move names and command lists, and the Theater captions.
- **Fonts** have open licences. The original bitmap fonts are not used.

## Graphics modernisation

**Principles**

- Keep the silhouettes, the timing and the colour identity of every stage and character.
- Remove the resolution and colour-depth limits.
- Replace flat 2D elements with vector ones where the original picture would only be stretched.

| Element | Original | Remake |
|---|---|---|
| Characters | Low-poly models, 4/8-bit textures, Gouraud lighting, rigid parts with seam blending | The same meshes as skinned meshes, lit with the game's normals (Shading: Original; a flat-lit face keeps its one normal) or by default with smooth ones (below), as `DrawSkinnedPart`'s NCCT lights them: the stage's back level, main light and light from below summed in display space, times the base colour, clamped, modulating the texel (`fighter_skin.gdshaderinc`, measured equal to the formula within 1.3 levels on average). Godot adds only the main light's shadows and the effects' point lights; no Godot ambient, SSAO or specular term (Godot's Fresnel raises even a faint one towards grazing angles, which makes dark polygons such as hair look like plastic). Texture filtering (the *Textures* setting): smooth (bilinear; the atlases' 2-texel gutters keep the regions apart; the floor with mipmaps) or crisp nearest for a retro look. The *Shading* setting: Original (the game's normals; the lighting formula above is measured with these), Smooth (the default; the converter's normals, `character.py` `smooth_normals`: at each point the normals of one joint are grouped transitively within 80° and summed; the normals of the seam's other joint (or a neighbour's) are a second half, added after skinning while the two halves agree within 80° in the current pose, `fighter_skin.gdshaderinc` `smooth_normal`) or Smooth + curved (also every triangle drawn as a 3 × 3 grid lifted onto its PN triangle after skinning its corners from a float texture, `curved_mesh.gd`, built once per model; edges that are not smooth on both sides, and hands' edges, stay straight so creases do not crack). Replacement texture packs (`user://texture_packs/<name>/<key>.png`, keyed by the converted picture's SHA-256; `tools/remake/texture_pack.py` dumps the originals and checks a pack) replace the converted pictures at any resolution, and a pack's `vram.json` the sprites the 2D screens cut from VRAM (page, texel rectangle, CLUT colours, checked against the SHA-256 of the VRAM words). DuckStation's page-mode replacement packs convert to this format (`texture_pack.py import-duckstation`, `duckstation_pack.py`): each replacement is found by its XXH3 hashes in the VRAM snapshots the converter records, its colours checked against the CLUT (DuckStation's palette hash covers too few colours to tell some CLUTs apart), and painted over the pictures it covers at its scale. |
| Lighting | One light matrix per stage, back colour, a decaying point light for fire and glows ([stages.md](research/code/stages.md#lighting), [effects.md](research/code/effects.md)) | A directional light (its shadows) and ambient light derived from the stage record for the floor; the fighters take the record's values directly (see Characters), including its base colour, which tints them per stage (0x80 neutral: stage 3's fighters are bluish against its yellow light, stage 0's warm). No tonemapping, so the unshaded panorama and the fighters show the game's colours. ### Aspect ratios

The original frames every shot for a 4:3 screen, and its scene only exists where a 4:3 camera could look: a 6 × 6 panorama grid around the arena with a per-stage height, an endless floor, and the clear colour behind them ([stages.md](research/code/stages.md#panorama)). The remake supports any window shape without showing more than the scene has.

**1. The original view is the reference.**

- The camera logic computes the same camera as the original: position, orientation and projection distance.
- Its 4:3 view rectangle is always fully visible, so the game shows at least what the player saw on the PlayStation, and never less.

**2. The view extends only where the scene exists.**

- The window's extra area beyond the 4:3 rectangle is sideways on wide screens (Hor+) and up and down on tall screens (Vert+).
- Each frame the `CameraRig` extends the view towards the window's shape as far as the scene covers it, and no further.
- **Coverage data.** For each stage the converter computes it from the panorama geometry: the elevation band covered by the panorama objects in every direction, seen from the arena area, and the directions where the grid leaves gaps. Only the faces turned to the arena count, since only they are drawn.
- **The floor covers everything below the horizon.** The only limits are above it (the sky edge of the panorama) and gaps between panorama objects.
- **Cinematic cameras.** Throws, hit cameras, round-end cameras and camera streams can look steeply up or down. The extension is computed per frame from the current camera, so these shots are limited the same way.
- **Result of the M2 check** (`remake/tests/support/coverage_report.gd` over the 15 stages' fight traces with fight, throw, hit, round-end and replay cameras): the panoramas of 14 stages close overhead in every direction once rays along the edges objects share count as hits and slits narrower than one 5° direction step (grid corners seen along a diagonal, which the 4:3 frame already shows) are ignored; before these two corrections single directions at 0°, 45° and 90° cut the extension on stages 2 and 4. Stage 11's panorama is low, but its clear colour is its sky, so it extends without limit. A tall window therefore extends upwards as far as the coverage allows and fills the rest downwards over the endless floor (an off-centre frustum), so the 4:3 frame, and with it the HUD, may sit above the window's centre.

**3. The rest of the window is framed.**

- Where the view cannot extend further, the remaining area is filled with the stage's clear colour, blending into the picture, or with neutral bars. This is a setting.
- The HUD always uses the full window with safe-area margins; only the 3D view is limited.
- A hard cap on the horizontal field of view (the width of 21:9) avoids fisheye distortion on very wide screens.

**Stages without a panorama** (the True Ogre arena draws only the clear colour and a spotlight floor) can extend freely, since the dark background is the intended look.

**Fairness.** Gameplay never depends on the extra area. Framing decisions stay those of the original 4:3 camera, and both players always see the same.

### Quality presets

| Preset | Renderer | Features |
|---|---|---|
| Web | Compatibility | Shadow maps (2k, 5-sample filter, larger biases against self-shadowing stripes), basic bloom, MSAA 2×; no SSAO or GI. |
| Mobile Standard / High | Mobile | Standard: shadows (2k), bloom, MSAA 2×, the 3D view at 85 % (bilinear: FSR is Forward+ only). High: soft 4k shadows, MSAA 4×, the 3D view at full size (the Mobile renderer has no SSAO or SSIL). |
| Desktop Low / High | Forward+ | Low: shadows (2k), bloom, MSAA 2×. High: soft 4k shadows, MSAA 4×, SSAO and screen-space indirect light (SSIL). |

The presets live in `presentation/render_quality.gd`; *Auto* picks the best one of the renderer in use (on phones the standard one). SDFGI and volumetric fog are left out: the stages are a textured panorama around a flat floor, without the geometry either would light or fill. Screen-space reflections are left out too: the floor is rough (no visible reflection, measured on the High preset). The fighters' cut-out texels (torn cloth, hair ends) are antialiased by alpha to coverage under MSAA (Forward+ and Mobile; the Compatibility renderer draws them as before); on the panorama it hid the hit flashes in front of it and improved nothing visible, so the panorama keeps its plain cut-out. Supersampling (the 3D view at 2×) and debanding were tried and left out: no visible gain at 1080p for +75 % GPU time, and no banding on the textured floors.

## Faithfulness and verification

**What must match the original frame for frame**

- Everything in `core`: move timing and transitions, frame events, root motion, collision shapes, damage, reactions, juggles, throws and reversals, round flow and timer, the camera director's decisions, AI decisions for given RNG states, mode rules, unlocks.
- Screen flow and timing: fades, waits, what Start skips.

**What may differ**

- Pixels, shading, effect appearance, UI layout details, audio mixing, loading times.

**Golden traces**

- `tools/research/export_traces.py` (to write) drives the verified Python ports (`fight_sim.py`, `pose.py`, `motion.py`, `camera_sim.py`, `ai_update.py`, `screens_sim.py`, ...).
- For each scenario it records the inputs and the resulting state per frame into `work/traces/`. Traces contain game data, so they stay in `work/`.
- The test suites replay the same inputs through `core` and compare the state field by field. A suite is skipped, with a message, when the traces are missing.

| Subsystem | Trace scenarios |
|---|---|
| Motion and pose | Every frame of every move of every bank (the ports already cover 314,290 frames). |
| Whole fights (M2) | 16 VS matches run in the game's own `FightMain` in the CPU harness (`fight_harness.py`: every character and stage, KO, time-out, draw, perfect, chip damage, a long match), compared every frame: every fighter field, joints, round flow, timer, camera, health bars, the random generators and the sound, vibration and music calls; the same 16 again with the Gameplay fixes patched in. |
| Moves and events | Scripted input sequences per character; the Enbu scripts. |
| Combat | Hit/guard/counter/juggle/throw sequences; random joint states as in `verify_fight_sim.py`. |
| Round flow, HUD timing | Full rounds: KO, time-out, draw. |
| Camera | Director with random sources; streams. |
| AI | Random records and states, seeded RNG, as in `verify_ai_sim.py`. |
| Screens and modes | `screens_sim.py`, `menu_sim.py` and `select_sim.py` scenarios; the whole game from boot in the game harness (`flow_trace.py`, M3). |
| Tekken Force and Tekken Ball (M4) | The game from boot through both modes (`flow_trace.py`: `ball`, `ball_versus`, `force`, `force_run`, `force_final`, `force_bosses`); the ports `force_sim.py` and `ball_sim.py` are verified against the game's own code (`verify_force_sim.py`, `verify_ball_sim.py`). |

**Bugs the remake does not reproduce.** The Python ports reproduce every original bug, so their traces can differ from the remake where a non-reproduced bug changes internal state (for example #47, or #17's unwritten stack word). The ports get a switch for these entries, and the traces are exported with the intended behaviour. The trace export fails if a scenario would depend on an entry that is not classified.

**Bug register.** New findings during the remake are added to `game-bugs.md` first, then classified below.

## Risks and open questions

| Topic | Risk | Plan |
|---|---|---|
| GDScript speed | The pose solver, collision and AI run every frame in GDScript. Rollback would multiply that work. | `Simulation.step` must stay below 2 ms on a mid-range phone and in the browser. M1's demonstration step takes 0.34 ms in the browser (desktop WebAssembly); phones are measured in M5. If it does not hold, profile first. Moving the hot paths to a GDExtension would break the GDScript-only decision and needs approval. |
| Web renderer | Only WebGL 2 (Compatibility) is supported officially; WebGPU exists in community forks only. | The Web preset targets Compatibility. Revisit when Godot ships WebGPU. |
| Controllers | Joypad input moved to SDL3 in Godot. Support on Android, iOS and the web in the pinned version needs checking. DualSense adaptive triggers are not supported. | Test DualShock 4 and DualSense over Bluetooth on every platform in M0 and M1. |
| Aspect ratios | Coverage limits computed from panorama geometry may be too strict (visible framing) or too loose (gaps at the edges in steep cinematic shots). | Build the coverage computation in M1 on stage 4 with a debug view of the covered area, then validate every stage in M2. |
| Legal | The code must not embed tables or texts taken from the game, and builds contain converted game data. | All game data, including the sine table and the EXE tables, goes through the converter. The exceptions, by the owner's decision (M5), are the generic English interface wording of the USA release (`content/texts_en.json`: SELECTED, RULES, HIT ANALYSIS, …) and the layouts of the other releases (`tools/remake_import/layouts/`: addresses, lengths and hashes, and the numbers of practice's page rows); names, titles, credits and pictures stay in the conversion. Tests read game data only from `remake/imported/` and the traces in `work/traces/`. Builds are private and not published. |
